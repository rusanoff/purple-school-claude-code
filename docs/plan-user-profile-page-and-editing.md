# Plan: Страница профиля пользователя и редактирование профиля

**PRD:** @docs/prd-user-profile-page-and-editing.md
**Дата:** 2026-09-05

## Фазы реализации

### Фаза 1: Профиль в модели данных и `GET /users/me`

**Цель:** Минимальный сквозной путь — у пользователя появляются поля профиля в БД, и их можно прочитать по JWT. Дальше на этом эндпоинте строится всё остальное.
**Затрагивает:** Database / Back-end
**Задачи:**

- [ ] Prisma: добавить в `User` опциональное `name` и опциональную ссылку на файл аватара + миграция
- [ ] `UserProfileResponse` (`id`, `email`, `name`, `avatarUrl`, `createdAt`) и маппер из Prisma-строки в `src/users/interfaces/`
- [ ] CQRS-запрос `GetUserProfileQuery` + handler в `UsersModule` (по паттерну существующего `find-user-by-email`)
- [ ] `UsersController` с `GET /users/me` под `JwtAuthGuard` и `@CurrentUser()`, регистрация контроллера в `UsersModule`
- [ ] e2e `test/users.e2e-spec.ts`: профиль с валидным токеном, 401 без токена; обновить `apps/backend/CLAUDE.md`

**Когда готова:** `GET /users/me` с валидным JWT возвращает `id`, `email`, `name`, `avatarUrl`, `createdAt` (у существующих пользователей `name` и `avatarUrl` — `null`), без токена — 401; e2e зелёные.

### Фаза 2: Страница `/profile` (просмотр) и переиспользуемый аватар

**Цель:** Пользователь видит свой профиль в UI и попадает на него из шапки главной страницы. Появляется компонент аватара, который дальше используется на всех экранах.
**Затрагивает:** Front-end
**Задачи:**

- [ ] `lib/users.ts`: тип `UserProfile` и `getUserProfile(token)` поверх `apiFetch`
- [ ] `components/avatar.tsx`: аватар с плейсхолдером-инициалом (имя → email), корректная работа при `name === null`; осознанный выбор между `next/image` и точечным исключением правила `core-web-vitals` для `<img>`
- [ ] `app/profile/page.tsx`: аватар, имя, email, дата регистрации; клиентский auth-gate, 401 → `/login`, состояния loading / error (+retry)
- [ ] Шапка `app/page.tsx`: аватар + имя (email как fallback) со ссылкой на `/profile`
- [ ] Проверка UI по «Definition of done for UI changes» + обновить `apps/frontend/CLAUDE.md`

**Когда готова:** `/profile` открывается залогиненным пользователем и показывает аватар/имя/email/дату регистрации, без токена и по 401 — редирект на `/login`; пользователь без имени и аватара отображается плейсхолдером-инициалом и email без пустых мест и ошибок в консоли.

### Фаза 3: Смена имени на backend

**Цель:** Имя профиля становится изменяемым через API, с валидацией на сервере.
**Затрагивает:** Back-end
**Задачи:**

- [ ] DTO смены профиля: `name` с обрезкой пробелов и валидацией минимальной/максимальной длины
- [ ] `UpdateUserProfileCommand` + handler: обновление `name`, возврат обновлённого профиля
- [ ] Маршрут `PATCH /users/me` под `JwtAuthGuard`
- [ ] e2e: успешная смена имени, пустое и слишком длинное имя → 400 с понятным сообщением, без токена → 401
- [ ] Обновить `apps/backend/CLAUDE.md` (эндпоинт и правила валидации имени)

**Когда готова:** `PATCH /users/me` меняет имя (пробелы по краям обрезаются), пустое/слишком длинное отклоняется с понятной ошибкой, `GET /users/me` отдаёт новое имя.

- [ ] Клиентская валидация длины до запроса; серверные ошибки — `danger` `Alert`, как на существующих формах
- [ ] Состояния операции: сохранение / успех / ошибка; после успеха имя обновлено в профиле и в шапке
- [ ] UI-проверка по чек-листу + обновить `apps/frontend/CLAUDE.md`

**Когда готова:** пользователь меняет имя через UI, после перезагрузки страницы новое имя отображается в профиле и в шапке главной страницы; пустое/слишком длинное имя отклоняется на frontend до запроса.

### Фаза 5: Аватар на backend — хранилище, публичная раздача, загрузка и удаление

**Цель:** Аватар можно загрузить, заменить и удалить через API, а картинка отдаётся по прямой ссылке без JWT — при этом приватные файлы встреч остаются закрытыми.
**Затрагивает:** Back-end
**Задачи:**

- [ ] Отдельные константы аватара: allowlist `image/jpeg`, `image/png`, `image/webp` и собственный, меньший лимит размера; отдельная env-переменная директории аватаров (не `FILE_STORAGE_DIR`) + `.env.example`
- [ ] Сервис хранения аватаров: сохранение потока под сгенерированным непредсказуемым (не производным от id/email) именем со своим лимитом размера, удаление частично записанного файла при превышении, удаление файла по пути
- [ ] Регистрация `@fastify/static` только на директории аватаров под публичным префиксом; зафиксировать, кто добавляет префикс `/api` к `avatarUrl`, чтобы путь резолвился через существующий frontend-rewrite
- [ ] Команды загрузки (`@fastify/multipart`, удаление предыдущего файла пользователя) и удаления аватара + маршруты `POST` / `DELETE /users/me/avatar`, `avatarUrl` в ответе профиля
- [ ] e2e: загрузка / замена (в директории ровно один файл на пользователя) / удаление, неразрешённый тип, превышение лимита без остатка на диске, доступ к URL аватара без `Authorization`, файлы встреч по-прежнему без токена недоступны; обновить корневой `CLAUDE.md` и `apps/backend/CLAUDE.md`

**Когда готова:** аватар загружается/заменяется/удаляется по API, при замене и удалении старый файл исчезает с диска, backend сам отклоняет неверный тип и превышение лимита, URL аватара открывается в браузере без заголовка `Authorization`, а `GET /meetings/:id/files/:fileId` без токена по-прежнему 401.

### Фаза 6: Аватар в UI

**Цель:** Пользователь загружает и удаляет аватар со страницы профиля, с превью до сохранения и валидацией до отправки.
**Затрагивает:** Front-end
**Задачи:**

- [ ] `lib/users.ts`: `uploadAvatar(token, file)` (`FormData`) и `deleteAvatar(token)`; зеркало allowlist и лимита размера + `validateAvatar(file)` и `accept` для пикера
- [ ] Зона загрузки аватара на `/profile` с превью выбранного файла до сохранения
- [ ] Удаление аватара с возвратом к плейсхолдеру-инициалу в профиле и в шапке
- [ ] Клиентская валидация типа и размера до запроса; состояния сохранение / успех / ошибка, серверные ошибки — `danger` `Alert`
- [ ] UI-проверка по чек-листу + обновить `apps/frontend/CLAUDE.md`

**Когда готова:** пользователь загружает jpeg/png/webp, видит превью до сохранения, после сохранения аватар виден в профиле и в шапке; удаление возвращает плейсхолдер везде; неверный тип и слишком большой файл отклоняются с понятной ошибкой ещё до отправки на сервер.

### Фаза 7: Смена пароля на backend

**Цель:** Пароль меняется по старому паролю, и клиент получает новый токен вместо разлогинивания.
**Затрагивает:** Back-end
**Задачи:**

- [ ] DTO смены пароля: старый и новый пароль, правила нового совпадают с `AuthCredentialsDto` (≥ 6 символов)
- [ ] `ChangePasswordCommand` + handler: проверка старого пароля через bcrypt, хэш нового теми же параметрами, что при регистрации
- [ ] Возврат **нового** `accessToken` из `TokenService` в ответе
- [ ] Маршрут смены пароля под `JwtAuthGuard`
- [ ] e2e: верный старый пароль (старый больше не логинится, новый логинится, выдан новый токен, ранее выданный токен остаётся валидным — принятый компромисс), неверный старый (пароль в БД не изменился), короткий новый, без токена; обновить `apps/backend/CLAUDE.md` (эндпоинт + отсутствие отзыва JWT)

**Когда готова:** смена пароля с верным старым паролем проходит и возвращает новый токен, с неверным — отклоняется с понятным сообщением и не меняет хэш, слишком короткий новый пароль отклоняется; e2e зелёные.

### Фаза 8: Смена пароля в UI

**Цель:** Пользователь меняет пароль со страницы профиля и остаётся залогиненным.
**Затрагивает:** Front-end
**Задачи:**

- [ ] `changePassword(token, { currentPassword, newPassword })` в `lib/users.ts`
- [ ] Форма смены пароля на `/profile`: старый пароль, новый, подтверждение нового
- [ ] Клиентская валидация: минимальная длина нового пароля (≥ 6, зеркалит backend) и совпадение подтверждения
- [ ] Сохранение нового `accessToken` в `localStorage` после успеха; состояния сохранение / успех / ошибка, неверный старый пароль — `danger` `Alert`
- [ ] UI-проверка по чек-листу, включая навигацию по приложению после смены пароля + обновить `apps/frontend/CLAUDE.md`

**Когда готова:** пользователь меняет пароль через UI, остаётся залогиненным (навигация не редиректит на `/login`), неверный старый пароль и слишком короткий новый показываются понятной ошибкой.

### Фаза 9: Имя и аватар автора файла и участников встречи на backend

**Цель:** API встречи отдаёт достаточно данных, чтобы показать «кто это» вместо email и «Meeting participant».
**Затрагивает:** Back-end
**Задачи:**

- [ ] Расширить `MeetingFileResponse` именем и `avatarUrl` загрузившего пользователя (без N+1 при выдаче списка файлов)
- [ ] Расширить ответ встречи: для каждого email из `participants` — имя и `avatarUrl`, если такой пользователь зарегистрирован, одним запросом на весь список
- [ ] Нормализация регистра email при сопоставлении участника с `User`, fallback на сам email для незарегистрированных
- [ ] e2e: список файлов отдаёт имя/аватар загрузившего (и fallback у пользователя без имени); встреча отдаёт профили зарегистрированных участников и голый email для остальных
- [ ] Обновить `apps/backend/CLAUDE.md` и корневой `CLAUDE.md` в части контракта ответов

**Когда готова:** `GET /meetings/:id` и `GET /meetings/:id/files` содержат имя и `avatarUrl` для зарегистрированных пользователей и корректно ведут себя при `name === null` и незарегистрированном участнике.
