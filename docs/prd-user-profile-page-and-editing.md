# PRD: User Profile Page and Profile Editing

**Дата**: 2026-09-05
**Статус**: Draft

## Цель

Дать зарегистрированному пользователю собственную страницу профиля, где он видит и может изменить свои данные — отображаемое имя, аватар и пароль. Аватар и имя затем используются везде, где приложение показывает «кто это»: в шапке главной страницы, в списке участников встречи и в списке загруженных файлов, вместо текущего голого email.

## Пользовательские сценарии

- Пользователь нажимает на свой email/аватар в шапке главной страницы -> попадает на страницу своего профиля с аватаром, именем, email и датой регистрации.
- Пользователь на странице профиля переходит к редактированию -> видит форму с текущим именем и аватаром.
- Пользователь меняет имя и сохраняет -> имя обновляется в профиле и в шапке главной страницы.
- Пользователь загружает новый аватар -> видит превью выбранного файла до сохранения, после сохранения новый аватар отображается в профиле и в шапке главной страницы, старый файл аватара удаляется.
- Пользователь удаляет аватар -> везде показывается плейсхолдер (инициал по имени или email).
- Пользователь вводит старый пароль и новый пароль -> пароль меняется, пользователь остаётся залогиненным (получает новый токен).
- Пользователь вводит неверный старый пароль -> изменение отклоняется с понятной ошибкой, пароль не меняется.
- Пользователь пытается загрузить аватар недопустимого типа или слишком большой -> получает понятную ошибку до отправки на сервер.
- Пользователь открывает страницу встречи -> видит участников и авторов загруженных файлов с их именами и аватарами вместо email/«Meeting participant».
- Неавторизованный пользователь открывает `/profile` -> редирект на `/login` (та же схема, что на главной и на странице встречи).

## В скоупе

**Модель данных**

- Поля `name` (опциональное) и ссылка на файл аватара (опциональная) у модели `User` + Prisma-миграция.

**Backend**

- `GET /users/me` — профиль текущего пользователя: `id`, `email`, `name`, `avatarUrl`, `createdAt`. Требует JWT.
- `PATCH /users/me` — изменение имени. Требует JWT, валидация длины и обрезка пробелов.
- Загрузка аватара (`multipart/form-data`) — сохранение файла в отдельную публично раздаваемую директорию под сгенерированным непредсказуемым именем, удаление предыдущего файла аватара пользователя.
- Удаление аватара — очистка ссылки в БД и удаление файла с диска.
- Смена пароля: приём старого и нового пароля, проверка старого через bcrypt, сохранение нового хэша, возврат **нового** `accessToken`.
- Отдельный allowlist MIME-типов для изображений (`image/jpeg`, `image/png`, `image/webp`) и собственный, меньший лимит размера аватара — независимо от allowlist'а файлов встреч.
- Публичная раздача статики для директории аватаров (`@fastify/static`), доступная через существующий frontend-прокси `/api/:path*`.
- Расширение `MeetingFileResponse`: имя и `avatarUrl` загрузившего пользователя.
- Расширение ответа встречи: для каждого email из `participants` — имя и `avatarUrl`, если такой пользователь зарегистрирован.
- E2E-тесты: получение профиля, смена имени, загрузка/замена/удаление аватара, смена пароля с верным и неверным старым паролем, работа старого и нового токена после смены пароля, отказ без токена.

**Frontend**

- Страница `/profile` — просмотр своего профиля (аватар, имя, email, дата регистрации), с клиентским auth-gate и обработкой 401 как на существующих страницах.
- Страница/режим редактирования профиля: поле имени, зона загрузки аватара с превью и удалением, форма смены пароля (старый пароль, новый пароль, подтверждение нового).
- Клиентская валидация до запроса: тип и размер аватара, длина имени, минимальная длина нового пароля (≥ 6, зеркалит backend), совпадение подтверждения.
- Состояния каждой операции: сохранение / успех / ошибка, ошибки сервера — `danger` `Alert`, как на существующих формах.
- Шапка главной страницы: аватар + имя (email как fallback, если имени нет) со ссылкой на `/profile`.
- Компонент аватара с плейсхолдером-инициалом, переиспользуемый на всех экранах.
- Список участников встречи и список файлов встречи показывают аватар и имя вместо текущих email / «You» / «Meeting participant».
- Сохранение нового токена в `localStorage` после смены пароля.

**Документация**

- Обновление корневого `CLAUDE.md` и `CLAUDE.md` обоих приложений в том же изменении (новая директория статики, новые эндпоинты, новые поля).

## Не в скоупе

- Изменение email и любая верификация email.
- Восстановление/сброс забытого пароля (по email-ссылке или иначе).
- Просмотр чужих профилей как отдельной страницы (аватар и имя другого пользователя видны только встроенными в списки участников и файлов).
- Кадрирование, поворот, ресайз и генерация превью аватара на сервере — файл сохраняется как загружен.
- Отзыв ранее выданных JWT при смене пароля (сессии на других устройствах остаются активными до истечения токена).
- Двухфакторная аутентификация, история входов, список активных сессий.
- Удаление аккаунта.
- Дополнительные поля профиля (телефон, часовой пояс, био, должность).
- Связывание `Meeting.participants` с моделью `User` через внешний ключ — остаётся `String[]` с email.
- Хранение аватаров во внешнем объектном хранилище (S3/CDN).

## Технические ограничения

- **Аватар раздаётся публично.** Файл лежит под сгенерированным непредсказуемым именем и доступен любому, у кого есть ссылка, без JWT — это осознанный выбор ради простого `<img src>`. Имя файла не должно быть перечислимым или производным от id/email пользователя.
- **Директория аватаров должна быть отдельной от `FILE_STORAGE_DIR`.** Там лежат приватные файлы встреч, доступ к которым проверяется по owner/participant — включать её в публичную раздачу статики нельзя ни при каких условиях.
- **Frontend не ходит на backend cross-origin** (см. корневой `CLAUDE.md`): URL аватара должен резолвиться через существующий rewrite `/api/:path*`, который **срезает префикс `/api`**. Нужно явно решить, возвращает ли backend путь уже с префиксом или его добавляет клиент, — иначе путь сломается на одной из сторон.
- Замена аватара обязана удалять предыдущий файл с диска, иначе директория копится осиротевшими файлами; удаление аватара — тоже.
- Аватары хранятся на диске backend-инстанса — то же ограничение горизонтального масштабирования, что уже зафиксировано для файлов встреч.
- **Allowlist файлов встреч (`isAllowedMimeType`) не подходит для аватара** — он не включает изображения и разрешает аудио/видео/документы. Нужен отдельный набор типов и отдельный, меньший лимит размера; и то и другое проверяется на backend независимо от frontend-валидации.
- `@fastify/multipart` уже зарегистрирован глобально, но `MeetingFileStorageService` завязан на встречи и на `FILE_MAX_SIZE_BYTES` — для аватара нужна своя логика сохранения (либо общий переиспользуемый примитив), а не вызов существующего сервиса как есть.
- Backend работает на Fastify, не на Express: Express-хелперы Nest для загрузки файлов (`FileInterceptor`, `@UploadedFile()`) неприменимы.
- Смена пароля должна требовать старый пароль и сверять его с `passwordHash` через bcrypt; новый пароль хэшируется теми же параметрами, что при регистрации.
- Правила валидации нового пароля должны совпадать с `AuthCredentialsDto` (сейчас ≥ 6 символов) на frontend и backend, иначе формы разойдутся с сервером.
- JWT stateless, механизма отзыва нет: после смены пароля ранее выданные токены остаются валидными до истечения `JWT_EXPIRES_IN`. Это принятый компромисс, но он должен быть зафиксирован в документации, а не «случайно так вышло».
- `Meeting.participants` — `String[]` со свободными email, не связанный с `User`. Резолв участника в профиль идёт сопоставлением email, поэтому: (а) несовпадение регистра email ломает сопоставление, (б) участник может не иметь аккаунта вообще — нужен fallback на сам email, (в) резолв не должен превращаться в N+1 запрос на каждого участника.
- Список файлов встречи сейчас показывает «You»/«Meeting participant», потому что backend не отдаёт ничего об авторе кроме `uploadedById` — показ имени/аватара требует расширения ответа на backend, только frontend это не решает.
- Пустое имя — валидное состояние (существующие пользователи создаются без него), UI обязан корректно работать с `name === null` везде, а не только на странице профиля.
- `eslint-config-next` (`core-web-vitals`) ругается на сырой `<img>` — нужно осознанно выбрать между `next/image` (с настройкой источника) и точечным исключением правила.

## Критерии готовности

- [ ] `GET /users/me` с валидным JWT возвращает `id`, `email`, `name`, `avatarUrl`, `createdAt`; без токена — 401.
- [ ] Пользователь меняет имя через UI, и после перезагрузки страницы новое имя отображается в профиле и в шапке главной страницы.
- [ ] Пустое/слишком длинное имя отклоняется с понятной ошибкой на frontend и на backend.
- [ ] Пользователь загружает аватар (jpeg/png/webp) через UI, видит превью до сохранения, и после сохранения аватар отображается в профиле и в шапке главной страницы.
- [ ] При замене аватара предыдущий файл удаляется с диска (в директории остаётся ровно один файл на пользователя).
- [ ] Загрузка файла неразрешённого типа отклоняется с понятной ошибкой и на frontend, и на backend (backend отклоняет запрос в обход frontend-валидации).
- [ ] Загрузка файла сверх лимита размера аватара отклоняется с понятной ошибкой на frontend и на backend, частично записанный файл на диске не остаётся.
- [ ] Пользователь удаляет аватар, и везде (профиль, шапка, списки) показывается плейсхолдер-инициал; файл удаляется с диска.
- [ ] Пользователь без аватара и без имени корректно отображается везде (плейсхолдер + email), без пустых мест и ошибок в консоли.
- [ ] Смена пароля с верным старым паролем проходит: старый пароль больше не подходит для `POST /auth/login`, новый — подходит.
- [ ] Смена пароля с неверным старым паролем отклоняется (401/400 с понятным сообщением), пароль в БД не меняется.
- [ ] Новый пароль короче минимальной длины отклоняется на frontend и на backend.
- [ ] После смены пароля frontend сохраняет новый `accessToken`, и пользователь остаётся залогиненным — навигация по приложению не приводит к редиректу на `/login`.
- [ ] URL аватара открывается в браузере напрямую (без заголовка `Authorization`) и отдаёт изображение.
- [ ] Приватные файлы встреч по-прежнему **недоступны** без JWT — публичная раздача статики не открыла к ним доступ.
- [ ] В списке файлов встречи для каждого файла показаны имя и аватар загрузившего; для пользователя без имени — fallback.
- [ ] В списке участников встречи показаны имя и аватар для зарегистрированных участников и сам email — для незарегистрированных.
- [ ] Открытие `/profile` без токена редиректит на `/login`; истёкший токен (401 в ответе API) обрабатывается так же, как на главной и на странице встречи.
- [ ] Backend покрыт e2e-тестами: получение профиля, смена имени, загрузка/замена/удаление аватара, смена пароля с верным и неверным старым паролем, доступ без токена.
- [ ] Корневой `CLAUDE.md` и `CLAUDE.md` обоих приложений обновлены: новые эндпоинты, новые поля модели, директория аватаров и её отличие от `FILE_STORAGE_DIR`, поведение токена при смене пароля.
- [ ] UI проверен в браузере на состояниях loading/error/empty/success и на узком и широком вьюпорте, ревью по `ui-ux-pro-max` выполнено (см. «Definition of done for UI changes» в `apps/frontend/CLAUDE.md`).
