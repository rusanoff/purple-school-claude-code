# Plan: Meeting File Upload and Display

**PRD:** @docs/prd-meeting-file-upload-and-display.md
**Дата:** 2026-08-23

## Замечания по скоупу

PRD подразумевает две вещи, которых пока нет в кодовой базе. Обе согласованы с пользователем перед составлением плана, поэтому включены в фазы ниже:

- Страницы `/meetings/[id]` во фронтенде нет (есть только список встреч, логин и регистрация). Фаза 3 создаёт её минимальную версию — иначе файловому UI негде быть.
- `GET /meetings/:id` сейчас проверяет доступ только по `ownerId`, поэтому участник сегодня вообще не может открыть встречу. Фаза 1 расширяет эту проверку до owner-или-участник, так как доступ к файлам использует то же правило.
- Эндпоинта удаления встречи нет. Критерий PRD «при удалении встречи удаляются и её файлы» проверяем только если такой эндпоинт существует, поэтому Фаза 2 добавляет минимальный `DELETE /meetings/:id` (только владелец), который также чистит файлы на диске (каскад в БД сам по себе файловую систему не трогает).

Для backend-фаз (1 и 2) e2e-тесты пишутся первым пунктом, до реализации: сначала тесты падают (эндпоинтов/логики ещё нет), затем реализация делает их зелёными. Это относится только к backend — у frontend-фаз (3–5) автотестов в репозитории пока нет (см. корневой `CLAUDE.md`), проверка там ручная по критерию «Когда готова».

## Фазы реализации

### Фаза 1: Backend-основа — доступ к встрече и загрузка файла (Tracer Bullet)

**Цель:** Проверить сквозную работу основной механики: общая проверка доступа owner-или-участник, схема `MeetingFile`, хранение на диске и один защищённый эндпоинт загрузки с валидацией.
**Затрагивает:** Back-end, Database
**Задачи:**

- [ ] E2E-тесты (пишутся первыми, до реализации — на старте красные): owner и участник каждый могут загрузить валидный файл; не-участник отклоняется (401/403); недопустимый MIME-тип отклоняется; файл сверх лимита размера отклоняется; `GET /meetings/:id` доступен участнику.
- [ ] Prisma-миграция: модель `MeetingFile` — связь many-to-one с `Meeting` (`onDelete: Cascade`), связь `uploadedBy` с `User`, плюс поля `filename`, `mimeType`, `size`, `path`, `createdAt`.
- [ ] Общая проверка доступа owner-или-участник: сопоставляет текущего пользователя (JWT) с `Meeting.ownerId` или `Meeting.participants` по email, без учёта регистра; используется и в эндпоинте встречи, и в новых файловых эндпоинтах.
- [ ] Обновить `GetMeetingHandler`, чтобы использовать эту общую проверку вместо скоупинга только по `ownerId` — участник сможет загрузить встречу.
- [ ] `POST /meetings/:id/files` — multipart-загрузка в локальное файловое хранилище, allowlist MIME-типов (аудио/видео + распространённые документы) и лимит размера проверяются на backend, метаданные сохраняются через CQRS-команду, доступ защищён проверкой owner-или-участник.
      **Когда готова:** E2E-тесты из первого пункта — зелёные. Владелец или участник может отправить `POST` с валидным аудио/видео или документом на встречу и увидеть созданную запись в БД и файл на диске; недопустимый тип, превышение размера и запрос не-участника отклоняются; `GET /meetings/:id` теперь работает и для участников.

### Фаза 2: Backend — список, скачивание, удаление, удаление встречи

**Цель:** Завершить жизненный цикл файлов на backend и удаление встречи, от которого он зависит.
**Затрагивает:** Back-end, Database
**Задачи:**

- [ ] E2E-тесты (пишутся первыми, до реализации — на старте красные): видимость списка/скачивания для владельца и участника; удаление своего vs чужого файла (403) для участника; владелец удаляет любой файл; удаление встречи убирает файлы с диска.
- [ ] `GET /meetings/:id/files` — список метаданных (имя, MIME-тип, размер, дата загрузки, автор) для владельца или любого участника.
- [ ] `GET /meetings/:id/files/:fileId` — скачивание/стриминг файла, доступ owner-или-участник, 404 если файл не принадлежит встрече.
- [ ] `DELETE /meetings/:id/files/:fileId` — владелец может удалить любой файл, участник — только свой (`uploadedBy` совпадает); удаляет и запись в БД, и файл на диске.
- [ ] `DELETE /meetings/:id` — только владелец; удаляет встречу (каскад в БД убирает записи `MeetingFile`) и явно удаляет файлы на диске до/вместе с этим.
      **Когда готова:** E2E-тесты из первого пункта — зелёные. Полный жизненный цикл файла (загрузка/список/скачивание/удаление) работает через API с корректной проверкой прав, а удаление встречи не оставляет осиротевших файлов ни на диске, ни в БД.

### Фаза 3: Frontend — страница встречи (Tracer Bullet)

**Цель:** Дать файловому UI страницу, на которой он будет жить, с базовой инфой о встрече и теми же правилами доступа, что и на backend.
**Затрагивает:** Front-end
**Задачи:**

- [ ] `app/meetings/[id]/page.tsx` — загружает встречу через `GET /meetings/:id`, следуя существующему паттерну проверки авторизации/загрузки из `app/page.tsx`.
- [ ] `lib/meetings.ts` — добавить клиентскую функцию `getMeeting(token, id)`.
- [ ] Базовый layout: название, дата, участники; ссылка на страницу с каждой карточки встречи на главной.
- [ ] Обработка ответов 401 (редирект на логин) и 403/404 (не-участник — состояние «доступ закрыт»).
      **Когда готова:** Владелец или участник может перейти из списка встреч на рабочую страницу встречи с её данными; не-участник на неё не попадает.

### Фаза 4: Frontend — загрузка и список файлов

**Цель:** Дать пользователю загружать файлы и видеть, что прикреплено, прямо со страницы встречи.
**Затрагивает:** Front-end
**Задачи:**

- [ ] `lib/files.ts` — клиентские функции для эндпоинтов загрузки (`multipart/form-data`) и списка.
- [ ] UI загрузки (file input/dropzone) с клиентской валидацией типа и размера до отправки, совпадающей с allowlist и лимитом на backend.
- [ ] Отображение состояния загрузки: в процессе / успешно / ошибка.
- [ ] UI списка файлов: имя, иконка типа, размер, дата загрузки, автор.
      **Когда готова:** Пользователь может загрузить валидный аудио/видео файл или документ со страницы встречи и увидеть его в списке с корректными метаданными; недопустимый тип или превышение размера отклоняются на клиенте с понятным сообщением ещё до отправки.

### Фаза 5: Frontend — скачивание и удаление

**Цель:** Завершить файловый UI, чтобы все критерии готовности из PRD были выполнимы целиком.
**Затрагивает:** Front-end
**Задачи:**

- [ ] `lib/files.ts` — добавить функцию скачивания, которая забирает файл как blob с bearer-токеном (обычная `<a href>` не пронесёт заголовок `Authorization`) и запускает сохранение через object URL.
- [ ] Действие скачивания привязано к каждой строке файла.
- [ ] Кнопка удаления — видна владельцу для любого файла, а каждому участнику — только для файлов, которые загрузил он сам; перед вызовом `DELETE` запрашивает подтверждение (AlertDialog с именем файла — удаление необратимо, стирает и запись в БД, и файл на диске), убирает строку из списка при успехе.
- [ ] Показ ошибок удаления (например, устаревший 403) без падения списка.
      **Когда готова:** Любой владелец или участник может скачать файл кликом; владелец может удалить любой файл, а участник — только свой, после подтверждения в диалоге, список обновляется сразу после каждого действия.

## Покрытие критериев готовности

| Критерий из PRD                                                         | Покрыт в               |
| ----------------------------------------------------------------------- | ---------------------- |
| Владелец/участник загружает аудио/видео запись                          | Фаза 1, Фаза 4         |
| Владелец/участник загружает документ                                    | Фаза 1, Фаза 4         |
| Недопустимый тип файла отклоняется (frontend + backend)                 | Фаза 1, Фаза 4         |
| Превышение лимита размера отклоняется (frontend + backend)              | Фаза 1, Фаза 4         |
| Не-участник не может загрузить/увидеть список/скачать/удалить (401/403) | Фаза 1, Фаза 2, Фаза 3 |
| Список файлов показывает имя/тип/размер/автора                          | Фаза 2, Фаза 4         |
| Владелец/участник скачивает любой файл                                  | Фаза 2, Фаза 5         |
| Владелец удаляет любой файл                                             | Фаза 2, Фаза 5         |
| Участник удаляет только свой файл (иначе 403)                           | Фаза 2, Фаза 5         |
| Удаление встречи удаляет её файлы (БД + диск)                           | Фаза 2                 |
| UI показывает состояние загрузки (в процессе / успешно / ошибка)        | Фаза 4                 |
