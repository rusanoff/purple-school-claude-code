# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See also the root `CLAUDE.md` for monorepo-wide conventions (shared lint/format config, port allocation). If you change this app's architecture, update the "Architecture" section below in the same change.

## Architecture

- `next.config.ts` sets `turbopack.root` explicitly to the monorepo root — this is required because Next's workspace-root auto-detection gets confused by lockfiles/config outside this repo; don't remove it.
- Styling is **Tailwind CSS v4** (via `@tailwindcss/postcss`, configured in `postcss.config.mjs` — there is no `tailwind.config.*`; Tailwind v4 is CSS-configured) plus **HeroUI v3** (`@heroui/react` + `@heroui/styles`). Both are imported in `app/globals.css` in that order (`tailwindcss` first, then `@heroui/styles`) — the order is required. `app/globals.css` is imported once, in `app/layout.tsx`.
- HeroUI v3 needs **no provider** and no `framer-motion`. Its components use the compound pattern (`Card.Header`, etc.), semantic variants (`primary`/`secondary`/`danger`/…), and `onPress` rather than `onClick`. Do not apply HeroUI v2 patterns — they are incompatible. Client components using HeroUI need `'use client'`.
- **Branding:** `components/brand.tsx` exports `APP_NAME` (`'Video Meetings'`, also the source of `metadata.title` in `app/layout.tsx`) and `<Brand />`, the logo + wordmark lockup. There is deliberately **no global header** on the auth pages — the layout renders only `{children}`, and pages that want the branding place `<Brand />` themselves (the register/login pages center it above the card); `app/page.tsx` renders its own compact header instead (logo + app name, the signed-in user as an avatar + name linking to `/profile`, log out). Full-bleed decorative backgrounds on the auth pages are `fixed inset-0 -z-10` so they cover the viewport regardless of the page's own height. `components/icons.tsx` holds every small inline SVG icon shared across pages (envelope, lock, eye, check, log-out, calendar, users, arrow-left, search-off, the video-camera logomark, upload-cloud, the file-type set music-note/film/document/file, x-circle, x, download, trash, pencil) — add new ones there rather than inlining `<svg>` in a page.
- **`components/avatar.tsx`** — `<UserAvatar name email avatarUrl size label />`, the one avatar used everywhere the app shows "who this is" (today the dashboard header and `/profile`; the meeting participant/file lists follow in later phases). It shows the uploaded picture when `avatarUrl` is set and an initial placeholder otherwise, falling back from `name` to `email` for that initial (both `UserProfile.name` and `avatarUrl` are nullable — see the `lib/users.ts` bullet above) so it is never blank; the initial is taken by code point, not UTF-16 unit, so a name starting with an emoji isn't split into half a surrogate pair. `getDisplayName(name, email)` is exported alongside it and applies the **same** name→email fallback, so a screen can't label someone one way and initial them another — use it rather than re-deriving the fallback per page. Built on HeroUI's `Avatar` (Radix-backed) deliberately, rather than `next/image` or a hand-written `<img>`: the avatar URL is only known after a client-side `GET /users/me`, so it can never be the LCP element, and Next's optimizer would add a Next→backend hop for a 32–96px image already served same-origin through the `/api` rewrite; a raw `<img>` would need a targeted `@next/next/no-img-element` disable (the `core-web-vitals` set) plus its own `onError`, whereas Radix preloads the URL off-DOM and only mounts the real `<img>` once it has loaded — so a deleted or broken avatar file keeps showing the initial instead of a broken-image icon (the browser still logs the failed image request itself, as it does for any 404, but nothing in the app throws or needs an `onError`). Sizes are `sm`/`md`/`lg` (HeroUI's 32/40/48px) plus `xl` (96px) for the profile page, which HeroUI has no variant for and which is therefore a Tailwind class override — that works because HeroUI ships its component CSS in `layer(components)` and Tailwind utilities land in the later `utilities` layer, so the override needs no `!important`. It is **`aria-hidden` by default**: every call site pairs it with the user's name, and announcing the name twice is worse than not announcing the avatar; pass `label` to make it `role="img"` with that accessible name when it ever stands alone. Note the dashboard header pairs it with a name that is `hidden` below `sm` and names the surrounding _link_ with an `aria-label` instead — a call site that hides its own name that way has to carry the accessible name somewhere, and doing it on the link keeps a single announcement at every width.
- **`components/profile-avatar.tsx`** — `<ProfileAvatar profile onSaved />`, the picture half of `/profile`'s card header and the only place the app writes an avatar. It wraps the `xl` `<UserAvatar>` in a drop target and puts an "Upload photo" / "Change photo" button under it; a picked or dropped file is **not** uploaded on selection but previewed first, rendered by `UserAvatar` itself with a local `blob:` URL, so what the user approves before saving is drawn by the same component that will draw the result — labelled "Preview — not saved yet", since otherwise nothing distinguishes it from a saved picture. Save calls `uploadAvatar` and hands the returned profile up through `onSaved`, exactly as `ProfileName` does with `updateProfile`: `POST /users/me/avatar` answers with the same shape as `GET /users/me`, so the page's `LoadResult` stays the one source of truth and nothing refetches. The file and its preview URL are **one** piece of state, so a render can never show one file's image above another's name, and the URL is revoked from an effect cleanup keyed on it — that covers replacing, cancelling, saving _and_ unmounting, which revoking at each call site would not. A pick landing mid-upload is refused outright: the in-flight request already carries the previous file, and swapping the preview under it would leave the card showing one image while the server stores another. The drop target is a shortcut, never the only way in (WCAG 2.2 "Dragging Movements" is satisfied by the button regardless) and it is named in the hint text, because nothing about a circle suggests you can drop on it. Clearing the selection returns focus to the upload button, since Save/Cancel unmount underneath the user — the same handover `ProfileName` does when its editor closes. Note the saved picture briefly falls back to the initial after a successful upload: the `src` changes from the `blob:` URL to `/api/avatars/...`, and Radix's `Avatar` resets to its fallback on any `src` change. A user who already has a picture also gets **"Remove photo"** next to that button (and only then — `DELETE /users/me/avatar` succeeds on an already-empty avatar, so a permanently-shown button would report doing something while changing nothing), which confirms through the same `AlertDialog` shape as `components/meeting-files.tsx`'s `DeleteFileButton` and for the same reason: the delete erases the stored file, so an accidental press costs the user their original. That dialog is rendered outside the branch holding the button rather than beside it — a successful removal clears `avatarUrl` and closes the dialog in one commit, and a dialog whose subtree is torn out in that commit never runs its exit or focus handling. Removal keeps its own pending/error state rather than sharing the upload's (the two can never run at once, but they report in different places, and one shared `error` would surface whichever failed last in both), and a failure keeps the dialog open with the reason inside it. Focus is then placed deliberately on the now-relabelled "Upload photo" button from an effect keyed on `profile.avatarUrl`, because the dialog's own restore target — "Remove photo" — is exactly what the removal unmounts; that races nothing, since React Aria's restore runs in a `requestAnimationFrame` and only acts when focus has landed on `<body>`. Nothing has to be done for the dashboard header: it reads the avatar from its own `GET /users/me` on mount, so navigating back to it after a removal already shows the initial. While the request is in flight every dialog control is disabled — the X included, unlike `DeleteFileButton`'s — because closing then would drop the outcome of a request that can't be called off, and a failure would set the error into a dialog nobody can see. A success is confirmed by a "Photo removed." `role="status"` region: the picture turning into an initial and a button relabelling itself are both silent to a screen reader. That region is rendered unconditionally so React keeps it mounted (one that appears together with its content is announced unreliably), and it is `sr-only` while empty rather than a bare empty node — it sits in a `gap-3` flex column, where a zero-height item is still an item and would space the avatar 12px further from the buttons on every visit. Its text is deliberately not `text-success`: that green measures 2.2:1 on the card, fine for the check icon it tints in `components/meeting-files.tsx` but not for 12px text.
- **Backend calls go through a same-origin proxy.** `next.config.ts` rewrites `/api/:path*` → `${BACKEND_URL}/:path*` (`BACKEND_URL` defaults to `http://localhost:3001`, see `.env.example`). The browser therefore only ever talks to this origin, which is why the backend needs **no CORS configuration** — don't add `app.enableCors()` there or switch the client to absolute backend URLs without removing this rewrite. Note the rewrite strips `/api`, so the frontend path `/api/auth/register` hits the backend route `POST /auth/register`.
- `lib/api.ts` is the shared low-level client: `apiFetch(path, { token, ...init })` fetches `/api<path>`, attaches a `Bearer` header when `token` is given, and throws `ApiError` on a network failure or a non-2xx response — `ApiError` normalizes Nest's error body (`message` is a plain string for thrown HTTP exceptions like the 409 on a duplicate email, and a string array for `ValidationPipe` failures). It only sets the default `Content-Type: application/json` header when `init.body` is a plain string (every current caller passes `JSON.stringify(...)`) — a `FormData` body (the multipart upload in `lib/files.ts`) needs the browser to set that header itself with the multipart boundary, which a hardcoded JSON one would break. `lib/auth.ts` (`register()`, `login()`, plus the `accessToken` `localStorage` helpers `saveAccessToken`/`getAccessToken`/`clearAccessToken`, `getCurrentUserEmail()`, which reads the `email` claim out of the stored JWT without verifying it — fine for display, never for authorization — and `getCurrentUserId()`, the same for the `sub` claim, used to tell the signed-in user's own uploads apart from others' in the file list), `lib/meetings.ts` (`getMeetings(token)` for `GET /meetings`, `getMeeting(token, id)` for `GET /meetings/:id` — the id is `encodeURIComponent`-escaped before it goes into the path; `Meeting.isOwner`, mirroring the backend's `MeetingResponse.isOwner` — computed server-side from `ownerId`, since a participant list isn't a reliable way to tell "owner" from "participant with the same read access" apart on the client, see the root `CLAUDE.md`'s meeting-files access notes — decides who sees the delete button for which files, see the `components/meeting-files.tsx` bullet below), and `lib/files.ts` (`uploadMeetingFile(token, meetingId, file)` — `POST /meetings/:id/files` as `multipart/form-data`; `listMeetingFiles(token, meetingId)` — `GET /meetings/:id/files`; `downloadMeetingFile(token, meetingId, fileId, filename)` — `GET /meetings/:id/files/:fileId`, fetched as a blob and saved via a throwaway `<a download>` object URL rather than a plain `<a href>`, since that can't carry the bearer token the route requires; `deleteMeetingFile(token, meetingId, fileId)` — `DELETE /meetings/:id/files/:fileId`, who's allowed to delete which file is enforced by the backend, not this client) all build on `apiFetch`. `lib/files.ts` also mirrors the backend's upload allowlist (`apps/backend/src/meeting-files/constants/file-upload.constants.ts`) and its documented default size limit (`FILE_MAX_SIZE_BYTES` in `apps/backend/.env.example`, 50MB, exported here as `MAX_FILE_SIZE_MB` — the one place that number is computed, reused by both `validateFile`'s rejection message and the dropzone's hint text so they can't disagree) — `validateFile(file)` rejects an invalid MIME type or an oversized file before any request is made, `FILE_INPUT_ACCEPT` feeds the picker's `accept` attribute, and `getFileCategory(mimeType)` (`'audio' | 'video' | 'document' | 'other'`) picks a file-list icon from the same allowlist; keep all of this in sync with the backend if either the allowlist or the size default ever changes — the backend re-checks both regardless, this is only a faster/friendlier client-side rejection. `lib/users.ts` (`getUserProfile(token)` — `GET /users/me`, whose profile comes back is decided entirely by the bearer token, so it can never read someone else's; its `UserProfile` mirrors the backend's `UserProfileResponse`; `updateProfile(token, { name })` — `PATCH /users/me`, same token-decides-the-row property, returning the updated profile in that same shape so a caller can refresh from it instead of refetching; plus `USER_NAME_MIN_LENGTH`/`USER_NAME_MAX_LENGTH` and `validateName(name)`, which reject an empty, whitespace-only or over-long name before the request — those bounds are a hand-kept mirror of the backend's `UpdateUserProfileDto`, exactly like `lib/files.ts`'s upload allowlist, so **change them in the same commit if that DTO changes** or the form will validate against a stale limit and surface unexplained 400s; both sides measure the _trimmed_ value) builds on `apiFetch` too, but note the one field that does **not**: `UserProfile.avatarUrl` already carries the `/api` rewrite prefix, because the backend emits it that way (`AVATAR_URL_PREFIX`) so the value drops straight into an `<img src>` — prefixing it again the way `apiFetch` does for API paths would break it. `name` and `avatarUrl` are both nullable (a user who never filled in a profile reads back `null` on both), so every consumer has to render that case rather than assume a name. Every authenticated fetch is client-side only, since the token lives in `localStorage`. `lib/format.ts` holds display formatting shared across pages (`formatMeetingDate`; `formatDay`, the same locale and `medium` date style with no time of day, for timestamps whose hour is noise rather than information — `/profile`'s "Member since", from `UserProfile.createdAt`; `formatFileSize` for `MeetingFile.size` in bytes) — add to it rather than redefining a formatter locally in a page.
- `app/register/page.tsx` and `app/login/page.tsx` are the auth screens — HeroUI `Form`s whose client-side rules mirror the backend's `AuthCredentialsDto` (valid email; register also enforces password ≥ 6 chars, login only requires non-empty since the backend's 401 doesn't say which field is wrong). Keep the register validation in sync if that DTO changes. Server failures render as a `danger` `Alert` above the fields; register's success swaps the card for a confirmation panel, login's success calls `router.push('/')`. Each links to the other (`Don't have an account?` / `Already have an account?`).
- `app/page.tsx` is the dashboard at `/` — client-only auth gate (no server-renderable data to defer to, since the token is in `localStorage`): a mount effect reads the token, redirects to `/login` if it's missing, and otherwise fires `GET /meetings` and `GET /users/me` together, redirecting to `/login` on a 401 from either (expired/invalid token) instead of showing an error. The two are awaited as one `Promise.all` purely so the page paints once both have settled — neither rejects (each keeps its own failure in its own state), and waiting is what stops the header's name from visibly replacing the email a moment after the rest of the dashboard has rendered. A **non**-401 profile failure is deliberately not folded into the meetings error banner: the header just falls back to the email in the token and the initial placeholder, which is what a user who never set a name sees anyway. (The 404-means-the-session-is-over rule that `/profile` applies is left to that page — see its bullet below — since it is the page actually about that profile.) Renders the header (`<UserAvatar size="sm">` + `getDisplayName(...)`, the whole thing one link to `/profile`, next to a log-out button), the full meetings list, a "Recent meetings" widget with the newest 3 (the API already returns newest-first), and empty/error(+retry) states. That header link carries an `aria-label`, because its name is `hidden` below `sm` (no room next to the wordmark and the log-out button on a phone) and the avatar is `aria-hidden`, which would otherwise leave it with no accessible name at all on a narrow viewport; its hover background is likewise the affordance that has to work below `sm`, where `hover:text-foreground` has no visible text left to recolour — and the `-m-1` beside that background's `p-1` keeps the padding out of the layout box so the header stays a single row at 375px. Every meeting card (both the main list and the "Recent meetings" sidebar) is a `next/link` to `/meetings/[id]`. The fetch-in-effect needs a targeted `eslint-disable-next-line react-hooks/set-state-in-effect` — see the comment at the call site before removing it.
- `app/meetings/[id]/page.tsx` is the meeting detail page — same client-only auth-gate shape as the dashboard (mount effect reads the token, redirects to `/login` if missing, otherwise calls `getMeeting`), read via `useParams<{ id: string }>()` since this is a client component (no server-side `params` Promise to unwrap). The fetch outcome is one `LoadResult` discriminated union (`success`/`forbidden`/`not-found`/`error`), not separate booleans — that's deliberate, see the type's doc comment: independent booleans let one catch branch set a state without clearing another, so two mutually-exclusive UI states could render at once after a retry that failed a _different_ way than the first attempt. The stored result is also tagged with the `meetingId` it was fetched for (`{ id, result }`), and the loading spinner renders whenever that tag doesn't match the current `meetingId` — since this page isn't remounted when navigating client-side between two different `/meetings/[id]` routes, without that check the previous meeting's content would stay on screen until the new fetch resolves. Response handling extends the dashboard's pattern: a 401 clears the token and redirects to `/login`, same as there; `forbidden`/`not-found` (the backend's owner-or-participant check, see the root `CLAUDE.md`) render one of two dedicated empty states instead of the generic error banner — "you don't have access" (`LockIcon`) for 403, "meeting not found" (`SearchOffIcon`) for 404, deliberately different icons so the two states don't read as identical. Anything else (network, 5xx) falls back to the dashboard's retry-able `Alert`; both this page's and the dashboard's Retry handler redirect to `/login` instead of silently no-op-ing if the token has gone missing since the last render (e.g. a logout in another tab). On success, renders title/date/participants (each participant as a `Chip`, keyed by index+email since the backend doesn't dedupe participants) inside a `Card`, above a "Back to meetings" link to `/`; below that `Card`, `<MeetingFilesSection isOwner={result.meeting.isOwner} meetingId={result.meeting.id} />` renders the meeting's files, `isOwner` deciding who sees the delete button for which files there.
- **`components/meeting-files.tsx`** — the meeting-file upload/list UI, rendered on the meeting detail page as `<MeetingFilesSection key={result.meeting.id} meetingId={result.meeting.id} />` — keyed on the meeting id specifically so a client-side navigation between two different meetings remounts it instead of leaking one meeting's file list/upload queue into another's (this page isn't itself remounted for that, see its own bullet above). `MeetingFilesSection` is the entry point: fetches `listMeetingFiles` on mount into one `FilesLoadResult` discriminated union (`success`/`forbidden`/`not-found`/`error`, same rationale and shape as the page's own `LoadResult`) — 401 redirects to `/login`, 403/404 (access revoked or the meeting deleted after the page's own meeting fetch already succeeded) render a compact `LockIcon`/`SearchOffIcon` empty state with no upload dropzone and no retry (both permanent for this meeting), anything else gets a retryable `Alert`. Renders `MeetingFileUpload` above the current list and prepends each newly-uploaded file to local state instead of refetching (the list is already newest-first, and an upload response _is_ the newest file) — that prepend callback is `useCallback`-memoized since `MeetingFileUpload`'s own internal memoization depends on its identity. `MeetingFileUpload` is a click-or-drag dropzone (native `<input type="file" multiple>`, `FILE_INPUT_ACCEPT`) that runs every selected file through `validateFile` before touching the network and tracks each one as its own row in a local upload queue — `'uploading'` (spinner) → `'success'` (check) or `'error'` (rejection reason, from `validateFile` for an invalid file, the backend's message for a failed request, or the same 401-redirects-to-`/login` handling as everywhere else on this page for an expired token), independently dismissible, plus a bulk "Clear finished". Queue item ids come from a `generateLocalId()` helper (tries `crypto.randomUUID()`, falls back to a `Date.now()`/`Math.random()` string) rather than calling `crypto.randomUUID()` directly, since that throws outside a secure context (non-HTTPS, non-localhost). The (unexported) `MeetingFileList` renders each file's name, a `getFileTypeIcon`-picked icon, `formatFileSize`, `formatMeetingDate`, its uploader — `getCurrentUserId() === file.uploadedById` renders "You", anything else "Meeting participant" (see the `lib/files.ts` bullet above — the backend doesn't expose an uploader's email anywhere the frontend can currently read, so this is deliberately not a fabricated name) — and per-row download/delete actions. `DownloadFileButton` wraps `downloadMeetingFile`; since that fetches a blob rather than navigating a link, it owns its own `idle`/`downloading`/`error` state (`Button`'s `isPending`) and renders a failure as an inline "Couldn't download" message next to the button rather than throwing. `DeleteFileButton` renders only when the caller passed `canDelete` for that file (`isOwner || file.uploadedById === currentUserId`, computed in `MeetingFileList` from the `isOwner` prop `MeetingFilesSection` receives from the page) and opens a HeroUI `AlertDialog` confirmation (danger status, the filename bolded in the body, explicit that this erases both the DB record and the on-disk file) before calling `deleteMeetingFile`. That dialog is fully controlled (`isOpen`/`onOpenChange` local state) instead of the component's implicit trigger wiring, because the confirm button has to run an async request and stay open on failure rather than closing immediately the way a `slot="close"` button would; a failed delete (e.g. a since-stale 403/404) renders inline via an `Alert` inside the dialog instead of throwing, leaving the file list itself untouched. A successful delete closes the dialog and calls `onDeleted(fileId)`, which `MeetingFilesSection` uses to filter the row out of local state — the mirror image of `handleUploaded`.
- `app/profile/page.tsx` is the signed-in user's own profile at `/profile` — same client-only auth-gate shape as the dashboard and the meeting detail page (mount effect reads the token, redirects to `/login` if it's missing, otherwise calls `getUserProfile`), and the same one-`LoadResult`-union-instead-of-separate-state-pieces reasoning as the meeting page (see that type's doc comment). Its union has only `success`/`error` because `GET /users/me` has no id to get wrong: a **404 is handled exactly like a 401** here — the token verified but the user row is gone, so the session is over — and both clear the token and redirect to `/login` rather than rendering a retry the user can't act on. Anything else (network, 5xx) gets the dashboard's retry-able `Alert`, whose Retry handler also redirects to `/login` if the token has since disappeared. Renders `ProfileAvatar` (`components/profile-avatar.tsx`, the `xl` `<UserAvatar>` plus its upload zone — see that bullet) next to an `<h1>` of `getDisplayName(name, email)` (so a user who never set a name is headed by their email rather than a blank line), above a `<dl>` of Email and "Member since". The heading and the email value deliberately use `wrap-anywhere` rather than the `truncate` the rest of the app uses for user-supplied text: this is the one page whose whole job is showing the user their own name and address, so an over-long name — or an email standing in for a missing one, which has no spaces to break at — has to wrap and stay fully readable instead of being clipped to an ellipsis. The heading is not static text but `ProfileName`, the page's (unexported) two-mode name-editing section: the `<h1>` plus an “Edit name” button (“Add name” when there isn't one) in view mode, and a `Form` with a `TextField` prefilled from `profile.name` in edit mode. The form sits in the heading's own slot rather than a section below it, since the value being edited _is_ the heading and rendering both at once reads as two different names on one card; the field is `defaultValue`-seeded (uncontrolled) and starts **empty** for a user who never set a name rather than pre-filling the email the heading falls back to, which is not their name and shouldn't be offered as one to save. The field validates through `validateName` (`lib/users.ts`) before anything is sent — React Aria surfaces the reason in its `FieldError` and blocks the submit, so an empty, whitespace-only or over-`USER_NAME_MAX_LENGTH` name never reaches the network at all; `isRequired` is what covers the plain-empty case, and `validate` still owns whitespace-only, which satisfies `required` but trims to nothing. A `Description` states the limit up front (the register form's password-hint pattern), and there is deliberately **no** `maxLength` on the input to go with it — silently truncating a pasted name is a worse answer than telling the user it is too long. `validateName`'s messages are worded as instructions (“Enter your name.”), matching the auth forms' field errors rather than `validateFile`'s verdict-style upload-queue text. Saving calls `updateProfile` and hands the returned profile back to the page through `onSaved`, which replaces the whole `LoadResult` — `PATCH /users/me` returns the same shape as `GET /users/me`, so the page keeps one source of truth for what it renders (the avatar beside the heading reads from it too) and nothing refetches. Edit mode carries an `<h1>` of its own (“Edit your name”, naming the mode rather than repeating the value in the field): it takes over the heading's slot, and this is the page's only heading, so leaving the form open would otherwise strip heading navigation of anything to land on. A failed save renders the auth forms' `danger` `Alert` above the field and moves focus to it, same as the register page, and clears it on the next keystroke so a stale reason can't outlive the fix; 401/404 end the session exactly as the page's own fetch does. Leaving edit mode returns focus to the button that opened it, since Save/Cancel unmount underneath the user. While a save is in flight Save swaps to a spinner and “Saving…” and Cancel is disabled; `handleSubmit` additionally returns early on `isPending`, because a one-field form still submits implicitly on Enter and `isPending` only disables the _button_ — without that guard a second Enter fires an overlapping `PATCH /users/me` whose response could land after the first and win. A success renders a `success` `Alert` (“Name updated”) inside a `role="status"` / `aria-live="polite"` region that both modes render at the same position, so React keeps that node mounted across the switch: a live region that mounts together with its content is announced unreliably, and a save is exactly the moment it would otherwise appear. It is `polite` because the new name is already on screen in the heading behind it, and it is cleared when the editor reopens so it can't re-assert a save the user has moved on from. One behaviour that was verified rather than authored, worth knowing before someone “fixes” it: `FieldError` follows React Aria's native validation, so a rejected name keeps its inline error while the user types and clears it on blur, while the save `Alert` clears on the first keystroke — the auth forms behave the same way, this is the framework default rather than an inconsistency introduced here.
- Lint config (`eslint.config.mjs`) extends the shared root base (`../../eslint.base.mjs`) plus `eslint-config-next` (`core-web-vitals` + `typescript` rule sets). Prettier formatting is enforced through ESLint (`prettier/prettier` rule from the shared base), not just as a separate step.

Any random UUID (e.g. `00000000-0000-0000-0000-000000000000`) against `/meetings/:id` with any logged-in fixture user gives the 404 "meeting not found" state; a request with no token (or a cleared `localStorage`) gives the 401 → `/login` redirect. Combine these 4 users with a real/nonexistent meeting id to hit every access state on the meeting detail page (success as owner, success as participant, 403 forbidden, 404 not found) plus the dashboard's empty/populated states, without registering anything through the UI first.

Re-seed (idempotent registration; skip a `register` call if it 409s — the user already exists, use `POST /auth/login` instead to get a fresh token):

```bash
PASS="QaPass123!"
for email in qa-owner@example.test qa-participant@example.test qa-outsider@example.test qa-empty@example.test; do
  curl -s -X POST http://localhost:3001/auth/register -H 'Content-Type: application/json' \
    -d "{\"email\":\"$email\",\"password\":\"$PASS\"}"
done

OWNER_TOKEN=$(curl -s -X POST http://localhost:3001/auth/login -H 'Content-Type: application/json' \
  -d "{\"email\":\"qa-owner@example.test\",\"password\":\"$PASS\"}" | python3 -c 'import json,sys;print(json.load(sys.stdin)["accessToken"])')

curl -s -X POST http://localhost:3001/meetings -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"title":"QA Sprint Planning","date":"2026-09-01T10:00:00.000Z","participants":["qa-participant@example.test"]}'
curl -s -X POST http://localhost:3001/meetings -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"title":"QA Retro","date":"2026-09-08T15:30:00.000Z","participants":["qa-participant@example.test"]}'
```

Every fixture user is seeded with `name: null` and `avatarUrl: null`, so logging in as any of them exercises the _no name, no avatar_ profile: the initial placeholder and the email standing in for the heading. **`/profile` can now write both** — pressing "Add name" or saving a picked photo as a `qa-*` user permanently changes what this table describes. The avatar is the recoverable one: `/profile`'s own "Remove photo" button puts `avatarUrl` back to `null` and deletes the file, and `curl -X DELETE -H "Authorization: Bearer $TOKEN" http://localhost:3001/users/me/avatar` does the same without the UI. The name is not — `PATCH /users/me` can't clear it, since the DTO's minimum length is 1 and there is no clear-the-name route — so restore that one in the database instead:

```bash
docker compose exec -T postgres psql -U postgres -d purple_school \
  -c "UPDATE users SET name = NULL WHERE email LIKE 'qa-%@example.test';"
```

To see the states that do have a name or a picture — and the error/loading states, which a healthy backend won't produce on demand — stub the response instead of touching the database: `page.route('**/api/users/me', ...)` via `browser_run_code_unsafe`, fulfilling with whatever `UserProfile` shape the state needs (a `name`, an `avatarUrl` plus a matching `**/api/avatars/**` route serving a real image, a 500 for the retryable error, a 401/404 for the redirect, a delayed fulfil for the spinner). Branch on `route.request().method()` inside that handler: the pattern matches on URL alone, and `/profile` now **writes** to the same URL, so an unguarded route swallows the save's `PATCH /users/me` too and every save silently succeeds or fails against the stub instead of the backend. That branch is also how the save's own states are reached — fulfil the `PATCH` with a 500 for the `danger` `Alert`, a 401/404 for the session-ended redirect, or after an `await page.waitForTimeout(...)` for the “Saving…” button — while `route.continue()` on the `GET` keeps the profile itself real. Keep all of it to verification only — the DB stays clean, so the fixtures keep meaning what this table says they mean.

To set a fixture user's token directly in the browser without going through the login form (useful for jumping straight to a state, e.g. the 403 view), get a fresh token via the `login` curl above, then in the Playwright MCP browser: `localStorage.setItem('accessToken', '<token>')` via `browser_evaluate`, then navigate.

## Definition of done for UI changes

Any change that affects the UI (pages, components, styling, layout, copy shown to users, interaction behaviour) is **not complete** until both of the following are done. Editing the code and having it compile is never enough.

1. **Verify it visually in a real browser.** The dev server is already running — do **not** start it (no `pnpm dev`, no `pnpm --filter frontend dev`) and do not restart it; just point the browser at the running app (frontend on `:3000`, backend on `:3001`). Only if the app is genuinely unreachable, say so instead of spawning your own server. Open the affected route with the Playwright MCP browser tools, and look at the rendered result — take a screenshot, exercise the interaction you changed (submit the form, open the modal, trigger the error state), and check the browser console for errors. Check the states that matter for the change, not just the happy path: loading, error, empty, and success where they exist, plus at least one narrow (mobile) and one wide (desktop) viewport for anything layout-related. Screenshots of what you actually saw are the evidence — do not claim a UI change works without having rendered it.
2. **Review it with the `ui-ux-pro-max` skill.** Invoke the skill and apply its guidance to the change (visual hierarchy, spacing, typography, colour/contrast, accessibility, responsive behaviour, interaction states). Fix what it surfaces, then re-verify visually per step 1. If you consciously deviate from a recommendation, say why in your summary.

Report the task as done only after both steps have actually run, and state in the summary what you rendered and what the skill review changed.
